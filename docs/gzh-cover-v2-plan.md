# 迭代方案 · 公众号双封面 v2:标题重新定级 + 单图交付

> 状态:**已实施 v1.26.0**(W1–W7 + 背景 L1 8 配方;实施细节见 CHANGELOG 与 `references/formats/gzh-cover.md`)。下文 §1 的「现状」为立项时快照。参考样本:18 张(桌面「迭代/公众号封面参考」)。
> 本方案先解决两件事:**标题排布按"手机小图"重做**,**默认只出一张合一图**。尺寸、六族版式、主题色板、拼接口径一律不动。
> §10 为增补:背景体系(18 张参考的背景语言如何落地),细则见 `references/gzh-cover-backgrounds.md`。

## 0. 一句话结论

现在的双封面是按"900×383 平面物料"在排:主标字号被 383 安全区卡死在 54–64px(占画布高 14%),又因为要凑满"不素"的 5–8 件元素,把眉题/副题/胶囊/水印/期号全塞上,结果在手机信息流里变成**一张缩小后看不清的小海报**。
18 张参考的共同解法是反过来的:**主标 3–9 个中文字、字高压到画布高的 18–32%(77–120px)、全图中文总数 ≤28 字、字体 1–2 款、附属信息 0–2 条**,并且**左右必然一起出片,永远是一张**。

因此本轮两处结构性改动:

1. **标题体系重写**:新增"文案预算"契约 + 字号阶按占画布比例重算 + 主标授权越过 383 安全区(带守卫条件),次条从"缩排"改为"提炼短标题"。
2. **交付形态反转**:`export` 默认只产 `cover-merged-<slug>.png` 一张;`--split` 才出主/次单张;`gzh_article.py convert` 同步。

## 1. 现状拆解(改之前的证据)

### 1.1 字号:被"平面字号阶"封顶

| 位置 | 现状 | 后果 |
|---|---|---|
| `scripts/_gzh_layouts.py:889` | `center-band` 主标 `base=54, floor=26, col=360` | 4 字标题也只有 54px(占画布高 14%),参考同位置约 120px |
| `:986` | `band-editorial` `base=60` | 同上,60px 是上限不是起步 |
| `:1075` | `stack-cards` `base=46` | 卡内 5 字/行,字号更小 |
| `:1335` | `plate-page` `base=50` | 有图族最保守 |
| `:865` `title_px()` | 按实际字宽反推,**但 `min(base, fit)` 永远不超过 base** | 短标题(2–4 字)本可以放大,却被 base 反向锁死 |
| `gzh_cover.py:1396` | 标题硬上限 20 个可见字符 | 20 字在手机上必缩成两行小字,等于鼓励写长 |
| `references/formats/gzh-cover.md §4.2` | 1–4 字 96–150 / 7–9 字 52–64 | 只有 `giant-caps` 敢给 96+,其余族实际拿不到 |

根因不是算错了,是**约束选错了对象**:`title_px(col=383)` 把"中央保守安全区 383px"当成主标最大行宽。参考图 18/18 都把主标铺到 600–750px 宽(约画布 67–83%),只在必要信息上守 383。

### 1.2 信息密度:按平面物料凑件数

- `gzh-cover.md §八` 要求元素 5–8 件(信息件 2–3 + 承载物 1 + 底纹 1–2 + 边缘物 0–2),这套是**印刷/长图**的丰满度标准;
- `§七-9` 允许"字体 ≤3 款、色相 ≤2、强调 ≤2";
- 六族默认模板里眉题 + 主标 + 副题 + 副题胶囊 + 英文水印 + 期号章 + 贴纸可同时出现。

参考图实测:**字体 1–2 款(18/18),中文总数 8–30 字(中位 18),附属层 0–2 条(18/18)**。方向是相反的——手机小图靠"字大、留白、单一视觉锤",不靠件数。

### 1.3 导出:三图齐出是默认

| 位置 | 现状 |
|---|---|
| `gzh_cover.py:2823` | `export` help:"默认三图齐出;--only 只出指定产物",`--only` 默认 `""` → main + sub + merged |
| `docs/gzh-guide.md:13,33-37` | 明写"三种导出 / 默认三图齐出",并在流程图里列出三个文件名 |
| `docs/gzh-guide.md:59` | "公众号后台上传仍用单张文件"——与实际使用场景相反 |
| `references/formats/gzh-cover.md §六` | "合并图是预览/汇报交付物"——定位被写反了 |
| `gzh_article.py convert` | 默认连封面一起出三图(`guide:16`),每篇多两次渲染 + 两次失败面 |

实测代价:一篇图文多渲染 2 张、多 2 个产物文件、多 2 处可能失败的检查点;而交付只需要 1 张。

## 3. 目标态规范(v2)

### 3.1 文案预算(先卡字,再谈字号)

| 槽位 | 硬上限 | 默认 | 说明 |
|---|---|---|---|
| 主标 | **12 个可见字符(中文 ≤9 最稳)** | 4–6 字 | 超过 12 字直接拒绝并给改写建议(替代现在的 20 字软上限) |
| 副题 | 12 字 / 1 行 | 0–1 条 | 允许缺失;缺了不许拿字形凑 |
| 眉题 | 中文 ≤6 / EN ≤24 字符 | 0–1 条 | 只作栏目提示,不得比副题更醒目 |
| 日期/地点等 meta | 1 行 ≤16 字 | 0–1 条 | 只允许 `plate-page` / 活动类 |
| 全图中文总数 | **≤28 字** | — | 信息流里超过 28 字必然缩水成小字 |
| 字体家族 | **≤2** | 1 | 第 2 款仅限手写/衬线点缀,且不承载信息 |
| 附属信息层 | **≤3**(主标 + 0–2) | 2 | 取代现在的"元素 5–8 件" |

与现行文档的冲突处理:`gzh-cover.md §八`「元素 5–8 件」改为**分层预算表**(标题承载物 1 必选、底纹 ≤1、边缘物 ≤1、信息件 1–3),同步 §七-9 字体 ≤3 → **≤2**。

### 3.2 字号阶(900×383 主封;按占画布高重算)

| 中文字数 | 目标字号 | 占画布高 | 行数 | 说明 |
|---|---|---|---|---|
| 3 | 124–127 | 33% | 1 | 参考 #9 的 33% 是上限 |
| 4 | 108–120 | 28–31% | 1 | 最常见的档(参考 1/7/8/13) |
| 5 | 96–108 | 25–28% | 1 | |
| 6 | 84–96 | 22–25% | 1 | |
| 7–8 | 72–84 | 19–22% | 1–2 | 两行时行高 1.05–1.12 |
| 9–10 | 64–72 | 17–19% | 2 | |
| 11–12 | 56–64 | 15–17% | 2 | 走 `band-editorial` 双行 |

实现上 **不是查表**,是把 `title_px()` 的 `base` 改为**按占画布比例反推的上限**(`base = 0.33 * 383` 起步),再受实际字宽与栏宽约束——保持"按字宽反推"的既有优点,只把上限从 54 抬到 127。

> 例外:`giant-caps` 现在的实际字号被二次压缩——`_giant_caps` 里 `main_px = min(106, int(300/longest), int(340/rows))`,4 字实测只有 **75px**(色块宽被限 383)。本表要生效,必须把这个 300/383 的上限随 §3.3 一起放到 720(色块允许越界),否则该族永远到不了 108px。

次条(383×383)**独立字阶,不再 ×0.62**:

| 次条标题字数 | 字号 | 行数 |
|---|---|---|
| 2 | 150–170 | 1 |
| 3 | 128–146 | 1 |
| 4 | 104–120 | 1–2 |
| 5–6 | 88–104 | 2 |

### 3.3 主标越界授权(带守卫)

安全区纪律从"主标必须整体在 258–642"改为**"语义必须守,字形可越"**:

- 主标行宽上限由 `383` 提升到 **720px(x≈90–810)**,按字号自然铺开;
- 守卫条件(三者同时成立才允许越界):
  1. **可见性**:主标至少有 `ceil(字数 × 0.6)` 个连续字符落在 258–642 内(即缩成方形缩略图时仍能读出主干);
  2. **辅助信息不越界**:副题、眉题、日期、胶囊一律仍限 258–642;
  3. **不压图**:越界方向若压到人物/商品主体,退回窄栏(由 `plate-page` 的图片安全窗判断)。
- 越界属于**显式授权**,`check` 输出新项 `title-overreach` 记录"越界了多少 px + 守住了多少字",不是静默通过。

### 3.4 右方区 = 标题提炼,不是缩排

- 改造**既有** `--sub-title`(该参数已存在,但默认值 = 主标题本身,`gzh_cover.py` new 的 help 里写着"次条标题(默认同主标题)"——这正是"缩排"的来源):缺省改为**自动提炼**(取主标前 2 组词 / 首尾各 2 字,失败回落主标前 4 字并提示),显式传入时按传入值渲染;
- 次条独立断行(不继承主标题的 `\n`),行数按上表;**绝不复用主标的 ×0.62 缩排**;
- 次条默认保留:底色 / 标题字体 / 承载形状;**删**竖排标签、英文水印、期号章、胶囊(与现行 §五-6 一致,继续保留)。

### 3.5 交付形态:一张图

| 场景 | v1 现状 | v2 默认 | 显式要求时才做 |
|---|---|---|---|
| `gzh_cover.py export <slug>` | 主 + 次 + 合并(3 张) | **只出 `cover-merged-<slug>.png`(1 张)** | `--split` 出主/次单张 |
| `gzh_cover.py merge` | 附加动作 | 保留(等价于"重导合并") | — |
| `gzh_article.py convert` | 封面三图 | **只出合并单图** | `--cover-split` 出三图 |
| 产物命名 | 3 个文件 | `cover-<slug>.png`(合并图专用名) | 单张仍用 `cover-main/sub-<slug>.png` |

尺寸**不变**:主 1800×766、次 766×766、合并 **2680×766**(scale 1,57×2 gap)。

> 平台兼容说明:若后台某场景必须上传 2.35:1 单张,用 `--split` 显式出图;这条写进文档,不做成默认。

## 10. 增补 · 背景体系与生图管线(2026-10-27 追加)

> 细则文件:`references/gzh-cover-backgrounds.md`(316 行,三层策略 + 8 个 CSS 配方 + 内联 SVG 规范 + 生图提示词规则 + 防伪文字三闸)。本节只记**方案层的改动与排期**,不重复配方代码。

### 10.1 为什么要加这一节

18 张参考的背景**全部有内容**:网点、格纹、牛皮纸、撕纸、票券、浏览器窗、放射光、幕布波浪、扁平插画、水彩、照片实景、3D 玩偶。而现行六个模板只有 `linear-gradient(135deg, --c-bg, --c-bg2)` 一层底(`_gzh_layouts.py:1040`、`:1119`)。**只改字号不改背景,做出来仍是"色块 + 大字"**,复现不了参考的观感。

### 10.2 三层策略(与"方案一优先"对齐)

| 层 | 手段 | 覆盖 | 优先级 | 依赖 |
|---|---|---|---|---|
| L1 CSS | 渐变/repeating-gradient/conic-gradient/clip-path/伪元素/mask/blend | 约 11/18(网点、格纹、纸纹、撕纸、票孔、窗框、放射、幕布) | **默认** | 无 |
| L2 内联 SVG | 手写 `<svg>`,颜色走 token | 扁平插画类(云山星音符相机牡丹胶带) | **次选** | 无 |
| L3 生图 | 图像模型出**无文字**背景 PNG | 照片/3D/复杂手绘(约 4/18) | 仅当 L1/L2 做不到 | 模型 + manifest |

判断顺序固定 **CSS → SVG → 生图**;L1+L2 覆盖约 14/18,生图是补丁不是主路。这正好回答"方案一是否可行":**可行,且大部分背景不需要生图**。

### 10.3 新增工作包

| 编号 | 工作包 | 内容 | 估时 |
|---|---|---|---|
| W6 | 背景配方落地 | 8 个 CSS 配方按族挂载(每族≤2 层伪元素)+ `assets/gzh-decor/` 首批 4 个内联 SVG + 背景预算校验 | 1 天 |
| W7 | 生图管线(可选) | `images/bg-*.png` + `bg-manifest.json` + 提示词模板 6 套 + 三闸验收 + `check` 增 `BG_MANIFEST_MISSING` | 0.5 天(仅在需要照片/3D 背景时启用) |

W6/W7 与 W1–W5 无写冲突:W6 改 `_gzh_layouts.py` 的模板 CSS,与 W2(字号)、W3(次条)、W4(导出)不同函数段;建议 W6 在 W5 回归前完成,这样回归样张自带新背景。

### 10.4 新增机检(接到 §5 清单后)

| 检查 | 判什么 | 阈值 |
|---|---|---|
| `bg-layer-budget` | 背景层数/纹理手法/色相 | 伪元素≤2、主纹理≤1、色相≤2 |
| `bg-text-safe` | 主标区(258–642)是否叠了高频背景或生图细节 | 只允许低对比渐变/纯色/压平层 |
| `bg-no-text-asset`(仅生图) | 有无 manifest 与 `text_free_checked` | 缺即 FAIL |
| `bg-offline` | 生图资产是否走本地相对路径 | 禁 `http(s)` 引用(既有 offline 校验已覆盖,新增仅提示) |

### 10.5 验收补充(接 §7)

7. 每族至少 1 张样张的背景是**内容层**而非纯渐变,且 15% 缩略图下第一眼仍是主标;
8. 生图背景(若启用)三闸全过:提示词含 NO TEXT、安全区压平层在位、15% 缩略图无"像字"残影;
9. 背景改动不引入 `check_slop.py` 的新 P0(尤其 `purple-gradient` / `trust-gradient` / `emoji-icon`)。

### 10.6 风险与回滚

- **风险 1:背景抢戏**。对策:§6 背景预算 + 15% 缩略图判据;超预算即回退到单层色底。
- **风险 2:生图不可复现**。对策:manifest 存提示词/模型/尺寸/日期与许可,`text_free_checked` 留痕;同 Brief 回归用固定资产,不重新生成。
- **风险 3:CSV/图片审计误伤**。`data:` URI 与内联 `<svg>` 已确认不被 `_is_external` / `media_elements` 拦截,但实施第一条 PR 必须先跑一次真实 `check` 留证。
- **回滚**:W6 的所有背景都挂在模板可选 class 上(如 `.bg-dots`),不写入基线 CSS;出问题删 class 即回旧观感,无需改 token。
